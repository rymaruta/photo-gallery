## 2. 新しい GSI は要るか

### 結論: **要らない。承認を求める必要も、いまは無い。**

スポット詳細が答える問いは4つで、**どれも DynamoDB を1回も引かない**:

| 問い | どう答えるか | 実行時の DB アクセス |
|---|---|---|
| このスラッグのスポットは？ | **静的HTML**（`generateStaticParams` が全スラッグを書き出し済み） | 0 |
| ふりがな・概要は？ | `content/spot-master.json`（ビルド時に埋め込み） | 0 |
| この場所の写真は？ | `photosInCollection`（`photos.json`・ビルド時） | 0 |
| 近くのスポットは？ | `nearbySpots`（`photos.json` の座標・ビルド時） | 0 |
| 自分は行きたいに入れたか？ | `GET /user/spots`（**既存**・`spots#<uid>` の `GetItem`） | 既存のまま（PK 一発・索引不要） |

`output: export` の静的サイトなので、**スポットのために新しい API を呼ばない**。
索引は「実行時に、鍵以外の列で絞る」ときに要るもので、この設計にはその経路が無い。

### 「何件のとき Scan では足りなくなるか」

仮に A 案（DynamoDB に台帳を置く）を採っても、読むのは
`scripts/sync-photos-from-ddb.js` の**ビルド時の Scan 1回**に相乗りする。

- DynamoDB の Scan は**1回の応答が最大 1MB**で、それ以上はページ送り
  （同スクリプトは既にページ送りしている）
- 台帳1件は 1KB 未満（14件で 14KB 未満）。写真は `photos.json` 上で
  1枚 809 バイト平均・30枚で 24KB
- **1ページ（1MB）に収まらなくなるのは、写真＋台帳が合わせておよそ千件を
  超えたあたり**（1MB ÷ 809バイト ≒ 1,295）。⚠️ **809 バイトは書き出した
  JSON の値で、DynamoDB の item はこれより大きい**（`stripPrivateFields` が
  落としたぶんがテーブルには残っている）ので、実際の千件はもっと手前。
  **桁の話として読むこと。** そして超えてもページが2枚になるだけで、
  **失敗はしない**——週1のビルドで数秒の差
- **GSI が要るのは「Lambda が実行時に、地域や近傍でスポットを絞る」経路を
  作ったとき**だけ。この設計はその経路を作らない

### 承認を求めるなら、こう書く（**いまは出さない**）

> 将来 `spotFeed` の GSI が要るのは、次の**どれかが起きたとき**です。
> 起きるまでは作りません。
>
> - スポットの一覧を**実行時に**（静的HTMLではなく API で）返す必要が出た
> - 台帳が数千件を超え、ビルド時の全件 Scan がビルド時間に響くようになった
> - 利用者がスポットを投稿するようになり、新着順の一覧が要るようになった
>
> そのときに足すのは `storyFeed-expiresAt-index` / `publicFeed-createdAt-index`
> と同じ形の**疎な GSI 1本**（台帳の行にだけ入れる定数 `spotFeed` ＋
> `updatedAt`）です。**保存量が台帳のぶんだけ倍**になります（14件なら
> 月 0.01 USD 未満）。作成には `api/serverless.yml` の変更と、本番・staging
> 両方への1回ずつのデプロイ（各 約4.5分）が要ります。ご承認をお願いします。

つまり「このスポットを誰が行きたいに入れたか」を**逆から引く道が無い**。

「行きたい 1人」というバッジは、正しくても**出す意味が無い**。

**→ 出さない。枠ごと出さない。** owner の指示「持っていない項目は欄ごと出さない」
に従う。将来出すなら a＋退会時の減算（もしくは b）を先に決める。

## 4. `/location/*` の URL・サイトマップ・`isIndexableCollection` への影響

### 影響は**ゼロ**。根拠は「触る場所が重なっていない」こと

`/location/*` の検索での姿は、**3か所だけ**が決めている:

| 決めるもの | どこ | 何を読むか |
|---|---|---|
| **どの URL のページが存在するか** | `app/location/[location]/page.tsx` の `generateStaticParams` → `lib/server/collections.ts:22 collectionStaticParams("location")` | `collectEntries(photos, "location").map(e => e.slug)` |
| **title・description・canonical・noindex** | 同ファイルの `generateMetadata` → `collectionMetadata("location", slug)` | `photosInCollection` の**枚数**と `isIndexableCollection(count, "location")`（＝2枚以上） |
| **サイトマップに載るか** | `app/sitemap.ts:69` | `collectEntries` ＋ `isIndexableCollection` |

この3つは**どれも `SpotPage` / `SpotPageClient` / `lib/utils/spot.ts` を
読んでいない**（`grep -rn "isIndexableCollection"` でスポット側に当たるのは
`SpotPage.tsx:11` の**コメント1行**だけで、呼び出しは0件）。
`app/location/[location]/page.tsx` が
`SpotPage` を呼ぶのは**本文（default export）だけ**で、
`generateStaticParams` と `generateMetadata` は素通り——これは
2026-09-21 にスポット詳細を入れたときの判断そのままで、今回も変えない。

### だから、守る規則を1つに絞る

> **`spot-master.json` の値（ふりがな・概要・別名）は、本文にしか出さない。**
> `collectionCopy` / `collectionMetadata` / `slugify` / `collectEntries` /
> `isIndexableCollection` の**引数にしない**。

これを破ると起きること（＝破らせないために書く）:

- 概要を `description` に流す → **`<title>` と `<meta name=description>` が
  14ページぶん変わる**。URL は変わらないが検索結果の見え方は変わる＝
  「SEO を壊さない」とは言えなくなる
- 別名を `slugify` に流す → **新しいスラッグが生まれ、ページが増える**

### 見張り（実装 PR に付ける）

1. **単体テスト**: `app/__tests__/` に1本。`collectionStaticParams("location")` と
   `app/sitemap.ts` の出力を、`spot-master.json` が**空のとき／埋まっているとき**で
   比べて**完全一致**を要求する。修正前（＝わざと `description` に流した版）で
   落ちることを確かめてから入れる
2. **実ビルドで数える**（`npm run verify` のビルド成果 `out/`）:

## この文書の何が生き、何が変わるか

owner から「判断は任せる」と言われたので、PM が次のように決めた。

### 生きるもの（1〜8節はそのまま有効）

- **`/location/*` は今まで通り。** URL・サイトマップ・`isIndexableCollection` の
  判定・`content/spot-master.json`（ふりがな・概要）は**1つも動かさない**
- **`savedSpots`（`spots#<uid>`）の鍵は撮影地のスラッグのまま。**
  ここを `spotId` に替えると、既に保存されている「行きたい場所」が全部外れる
- **数えられない統計は出さない**（行きたい人数・人気順・評価・口コミ）
- **`/location/*` の SEO を決める3経路に、新しい台帳を読ませない**

### 変わるもの

**7節の「`spotId` を作らない」を取り消す。** ただし**役割を分ける**:

| | 何を表すか | 鍵 | URL | 誰が作るか |
|---|---|---|---|---|
| **集約ページ** | 写真の `location` から作る**地域・撮影地** | 撮影地のスラッグ | `/location/<スラッグ>` | ビルドが写真から導出 |
| **スポット** | **個別地点**（緯度経度で一意） | `spotId` | **未定**（下） | 人が台帳に書く |

**この2つは別物として並立する。** 指示書の「地域と個別地点を同じデータとして
扱わない」がそのまま線引き。

- 「パリ」「フランス」は**地域** → 集約ページのまま。`spotId` を与えない
- 「高屋神社」「オペラ・ガルニエ」は**個別地点** → `spotId` を持つ
- **同名異所は別 `spotId`**（指示書）。集約ページは字の一致で寄せるので、
  ここが2つの仕組みを分ける最大の理由になる

### 決めていないこと（実装の前に決める）

1. **スポットのページを持つか。** 7節は「`/spots/*` を作らない」と書いたが、
   `spotId` を持つ以上は表示先が要る可能性がある。**ただし `/location/*` と
   内容が重なるページを2つ作るのは、いまも反対**——まず「スポット詳細の中で
   `spotId` の情報を使う」で足りないかを確かめること
2. **写真と `spotId` の紐付け**。指示書 6 が**最重要**として、
   名称一致だけで確定にしないこと・`--apply` を実行しないことを求めている。
   **未紐付け／候補／曖昧／人が確認済み**の4状態を区別する
3. **台帳の置き場。** `app/data/` は**ビルドが上書きする棚**（#109 で実測）なので
   人が書くものは置けない。`content/` に置くのがこのリポジトリの既定
