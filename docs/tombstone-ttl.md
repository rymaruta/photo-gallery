# 退会の墓石の TTL と、名前の写しの伏せ（札 rymaruta/journey.photo-ios#295・2026-10-18）

退会すると users テーブルの行は **墓石**（`{userId, deletedAt, ttl, username}`）に
置き換わる（`api-user/src/account.ts` の `deleteAccount`）。`ttl` は退会＋365日
（`TOMBSTONE_RETENTION_DAYS`・`tombstoneTtl()`）だが、**users テーブルの TTL はまだ有効にしていない**。

このページは「TTL を有効にする前に何が要るか」と「有効にする手順」をまとめる。
**有効にする日は owner が決める。この文書を書いた時点では何も有効にしていない。**

## 1. なぜ、先に写しを伏せるのか

他人の行に **書いた時点の表示名を写して持つ** 口がある。退会しても写しは消えず、今は
**読むたびに墓石を引いて**「退会したユーザー」に伏せている（`api-user/src/notify.ts` の
`deletedAmong`）。墓石が TTL で消えると「行が無い＝生きている人」と読まれ、
**退会した人の実名が公開の口（未認証のコメント一覧など）に戻る**。伏せも警告も出ない。

## 3. 2026-10-18 判断

**退会の処理では写しを書き換えない。読むときに伏せる今の作りは残し、墓石が消える前に
台本（`scripts/scrub-deleted-names.js`）で写しそのものを伏せる。**

- 退会の時に書き換えるには「その人の写しがどこにあるか」が要るが、上の表のどれにも
  人ごとの索引が無い。退会のハンドラの中で表を全部走査すると、あのハンドラが
  避けている「実行時間を使い切って返らない」に落ちる。新しい GSI は承認制で、
  写しのためだけに作る理由は薄い
- 読むときの伏せは墓石が在る間は正しく、退会した直後（台本がまだ流れていない間）も効く。
  足りないのは「墓石が消えたあと」だけで、そこを台本が埋める:
  写しの名前を `退会したユーザー` に書き換え、**`deleted: true` を写しに刻む**。
  コメント・通知・返信の読む口は写しをそのまま返すので印が素通しで届く。閲覧者の口
  （`getStoryViewers`）だけ形を組み直していたので、印を見るようにした（`stories.ts:664`）
- 本文（コメントの `text`・返信の `text`）は伏せない。`account.ts` の「v1 スコープ外」の
  判断（他人の写真に散在する自分のコメントは消さない）のまま。uid も残す（`/users/<sub>` は
  公開ルートで、sub は秘密ではない）

## 4. 台本 `scripts/scrub-deleted-names.js`

- **既定は読むだけ**: 墓石の数・ttl を持たない墓石の数・いちばん早く期限が来る日・
  種類ごとの「伏せる写し」の行数と件数・読み取り（この回で使った量）と書き込み（`--apply` で
  使う見込み）を出す
- `--apply` で書く。生きている人を守る仕組み:
  1. 対象は users テーブルの墓石（`deletedAt` が文字列）の人だけ
  2. 写しの**要素1つずつ**を番地で書く（`items[3].name`）。配列を丸ごと書き戻さない。
     番地の要素がまだその人のもの（`items[3].uid = 退会者`）であることが条件
  3. 同じトランザクションで墓石がまだ在ることを確かめる（`restore-account` で戻された人は書かない）
- 何度流しても同じ結果（伏せ済みは数えない・書かない）。条件が外れた回は飛ばして
  終了コード 1。もう一度流せば読み直して入る
- 行はページごとに読んで書く（表を全部メモリに貯めない）。メモリに持つのは退会者の ID の集合だけ
- **書いた回数は保証ではない。** アプリ側の切り詰め（`notify.ts:352` の通知・`comments.ts:324`・`:386` の
  コメント・`storyReplies.ts:272` の返信）は配列を**丸ごと書き戻す**。台本が書いた直後に、伏せる前に
  読んだ配列で上書きされると古い名前に戻る（窓は短いが在る）。**apply のあとは必ず読むだけで
  もう一度流し、伏せる写しが 0 件になったことを確かめる**（台本の最後の出力もそう言う）
- 実行の口: Maintenance ワークフローの `scrub-deleted-names`（本番）と `scrub-deleted-names-staging`
  （staging）。どちらも既定は読むだけ・apply で書く。**まず staging で読むだけ → apply → 読むだけ（0 件）**
  を通し、本物の DynamoDB が式を受け付けることを確かめてから本番に流す
- **staging に退会者の写しが無いと、式を一度も送らないまま緑になる**（読むだけでも apply でも
  「0 行 / 0 件」で終わる）。staging で試す前に写しを作っておく:
  1. staging で試しの利用者を作る
  2. その人で、**別の人の写真へのコメント**・**いいね**（相手に通知が積まれる）・
     **ストーリーの閲覧**・**ストーリーへの返信**を残す（返信と閲覧はストーリーの期限 24 時間の
     うちに次へ進む。期限が過ぎると掃除が行ごと消す）
  3. その人を退会させる（墓石が立つ）
  4. 読むだけの回で、**コメント・ストーリー返信・通知・閲覧者の4行すべてが「1 行 / 1 件」以上**
     あることを確かめる。どれかが 0 なら、その種類の式は試されないので apply に進まない
  5. apply → 読むだけ（4種類とも 0 件）
- **権限**: Actions の鍵（`AWS_ACCESS_KEY_ID`）に、photos 表の `Scan`・`UpdateItem` と、users 表の
  `Scan`・`ConditionCheckItem`（トランザクションの中の墓石の確かめ）が要る。足りなければ
  AccessDenied で止まる（トランザクションなので途中まで書いた状態にはならず、データは壊れない）。
  2026-10-18 時点で、この鍵の権限は確かめていない
- **戻した人の写しは伏せたまま**: `restore-account.js` で墓石を消して戻した人の写しは、台本が
  既に書いた分は `退会したユーザー`・`deleted: true` のまま残る（元の名前は書き換えたので戻せない）。
  読む口は印を見て伏せ続ける。戻したあとの新しいコメント・通知は普通に名前が出る。
  台本を流したあとで戻すときは、このことを本人に伝える

**費用の目安**: photos と users を1回ずつ全走査する（読み取りは表の大きさに比例。
結果整合で 4KB あたり 0.5 単位）。書き込みはトランザクションなので通常の2倍
（行の大きさ 1KB あたり 2 単位＋墓石の確かめ1件 2 単位）。コメントの文書は最大 350KB
なので、大きい文書1つで 700 単位前後になりうる。読むだけの回で見込みが出る。

## 5. TTL を有効にする手順（owner の許可のあと）

**どの表・どの属性**: `prod-photo-gallery-users`（staging は `staging-photo-gallery-users`）の
`ttl`（数値・epoch 秒）。

**serverless.yml ではなく手作業（AWS CLI）**。users テーブルは serverless の `resources` では
なく `scripts/provision-env.js` が作っていて（`ensureUsersTable`）、そこにも TTL の定義は無い。
serverless.yml に足しても表を持っていないので効かない。

1. 台本を**読むだけ**で流し、件数と量を見る（Maintenance → `scrub-deleted-names`・apply なし）
2. owner の許可を得て `--apply` で流す。終了コード 0（飛ばした回が 0）になるまで繰り返す
   （その前に staging で `scrub-deleted-names-staging` を同じ順で通しておく。**staging には先に
   退会者の写しを4種類とも作り、読むだけの回で4種類すべてが1件以上あることを確かめてから
   apply する**——無いと式を一度も送らないまま緑になる。作り方は §4 の「staging に退会者の
   写しが無いと」）
3. もう一度読むだけで流し、伏せる写しが **0 件** になったことを確かめる（書いた回数では判断しない。
   上の「書いた回数は保証ではない」）
4. TTL を有効にする（1回だけ。表ごとに1つしか持てない）:

   ```sh
   aws dynamodb update-time-to-live \
     --table-name prod-photo-gallery-users \
     --time-to-live-specification "Enabled=true,AttributeName=ttl"
   aws dynamodb describe-time-to-live --table-name prod-photo-gallery-users   # ENABLED を確かめる
   ```

5. **以後も台本を定期的に流す**（墓石の寿命 365 日より十分短い間隔。例: 月1回）。
   TTL を有効にしたあとに退会した人の写しも、この台本でしか伏せられない。
   1人ぶんの写しは、退会から1時間（配ったトークンの期限）が過ぎたあとに1回流せば足りる

**気をつけること**:

- **有効にすると、既にある墓石にも効く**（`ttl` を前から書いているので）。
  「これから退会する人だけ」にはならない。台本の読むだけの回が、いちばん早く期限が来る日を出す
- `ttl` を持たない墓石（書き始める前に退会した人）は、TTL を有効にしても消えない
- DynamoDB の TTL は期限ちょうどには消さない（期限のあと数日以内に消す）。消える前の行は
  読めるので、伏せの判定は今までどおり効く
- 有効にした直後の 1 時間ほどは、もう一度 `update-time-to-live` を呼べない（AWS の制限）
- 無効に戻しても、もう消えた墓石は戻らない（PITR から戻すしかない）
