## 🔴 この指示書で変わったこと（PM の追記）

### 1. 撮影スポットは「独立した spotId」で持つ — 今日の決定を上書き

指示書 5 に **「撮影スポットは独立した spotId を持つ個別のデータとして管理してください」**
「同名の別の場所は別 spotId に」「同じ場所の別名は同じ spotId へ」とある。

**これは今日の判断と逆向き。** `docs/spot-master.md`（#105）は
「**第二の ID を作らない・撮影地のスラッグを鍵にする**」で設計し、
そのまま本番へ出した（`c39a372d`）。理由は `savedSpots` と `/location/*` の SEO が
割れること。

指示書はその点も踏まえていて、**両方を並立させる**と書いてある:

| | 何を表すか | 維持 |
|---|---|---|
| `/location/*` | 写真の自由入力 `location` から作る**地域・撮影地の集約ページ** | **引き続き維持** |
| 新しいスポット | **個別地点のマスタ**（`spotId`） | 新設 |

**「地域と個別地点を同じデータとして扱わない」**が指示書の言葉。
つまり今日出したものを壊すのではなく、**その隣に個別地点のマスタを足す**。

- `content/spot-master.json`（ふりがな・概要）は `/location/*` 側の持ち物として残る
- `spotId` 側は PR #63 の実装を**再利用**し、ゼロから作り直さない
- **`/location/*` の URL・サイトマップ・noindex の判定は動かさない**

### 2. API を含む PR の develop マージに、事前承認が要る

指示書 0 の「事前承認が必要」に **「API 変更を含む PR の develop へのマージ」**が入った。
これまで PM は `api-user/**` を含む PR を develop へマージしてきた（#115・#119）。
**今後は owner の承認を取ってから。**

対象: `api/**` `api-user/**` を1行でも触る PR。
承認が要らないもの: `app/**` `lib/**` `scripts/**` `docs/**` だけの PR。

### 3. 写真とスポットの紐付けは「候補」と「確認済み」を分ける（最重要）

指示書 6。**名称一致だけで `confirmed` にしない。**
`scripts/link-photos-to-spots.ts` の `--apply` は**実行しない**。
書き込み側で**確認済み以外を拒否する**（警告だけでは不十分）。
