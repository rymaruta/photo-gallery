## 3. 公式ガイドとユーザー投稿を分離したデータ設計

### 方針

**`Spot`（#132）を土台に、公式ガイドの項目を足す。** 新しい型は作らない。
`SpotMasterEntry` の3項目（`reading` / `summary` / `aliases`）は `Spot` に
既に在るので、**`spotMaster.ts` は廃止して `spots.ts` に一本化**する。

### 足す項目（依頼の項目名 → 既存の命名に合わせた名前）

| 依頼 | 実装名 | 型 | 備考 |
|---|---|---|---|
| officialName | `name`（既存） | string | 既存優先 |
| publicCoordinates | `coords`（既存） | {lat,lng} | 約1km丸め済み |
| highlights | `highlights` | `string[]` | 見どころ。**箇条書き**（長文を1つにしない） |
| seasonalGuide | `seasonalGuide` | `{ season: "spring"\|"summer"\|"autumn"\|"winter"; text: string }[]` | 季節ごとの景色 |
| timeOfDayGuide | `timeOfDayGuide` | `{ time: "dawn"\|"morning"\|"day"\|"goldenHour"\|"dusk"\|"night"; text: string }[]` | 時間帯 |
| compositionTips | `compositionTips` | `string[]` | 代表的な構図 |
| accessInfo | `access` | `{ transit?: string; car?: string; walk?: string }` | 公共交通／車／徒歩 |
| parkingInfo | `parking` | `{ available?: boolean; note?: string }` | **料金は書かない**（変わる） |
| safetyNotes | `safetyNotes` | `string[]` | 立入禁止・撮影制限 |
| officialWebsiteUrl | `officialWebsiteUrl` | string | |
| nearbySpotIds | `nearbySpotIds` | `string[]` | **手で指定**。座標からの導出（`nearbySpots()`）は補助に残す |
| coverImage | `coverImage` | 下記 | **ユーザー写真とは別管理** |
| verifiedAt | `verifiedAt` | ISO 文字列 | `verified: boolean` を**日付に格上げ** |
| （新規） | `sources` | 下記 | **項目ごとの出典と確認日** |

### 出典と確認日（依頼の中核）

```ts
type SpotSource = {
    /** どの項目の裏付けか（"access" / "parking" / "safetyNotes" …） */
    field: string;
    url: string;
    /** 出典の名前（「観音寺市 公式サイト」） */
    title?: string;
    /** 確認した日（ISO） */
    checkedAt: string;
};
```

**規則**: `access` / `parking` / `safetyNotes` / `officialWebsiteUrl` は
**その項目の `sources` が1件以上ないと画面に出さない**。
「未確認の営業時間・駐車料金・所要時間・交通規制・撮影制限を推測で埋めない」を、
**表示の側で機械的に効かせる**（人の注意力に頼らない）。

営業時間・料金はそもそも**項目を作らない**——変わりやすく、間違えると
実害が出る。必要なら `officialWebsiteUrl` へ送る。

### 代表写真（§4 の要件）

```ts
type SpotCoverImage = {
    /** 画像の保存先。サイト内に置いたものだけ（外部ホットリンクはしない） */
    src: string;
    /** 縦横比（レイアウトを崩さないため。無ければ 3:2 で置く） */
    aspectRatio?: number;
    alt: string;
    /** 撮影者・権利者 */
    credit: string;
    /** 出典（どこで許諾を確認したか） */
    sourceUrl?: string;
    /** 利用許諾。**"owner" 以外は必ず `credit` を画面に出す** */
    license: "owner" | "cc-by" | "cc-by-sa" | "permission-granted";
    /** 画面に必ず出すクレジット表記（許諾の条件） */
    requiredCreditText?: string;
    /** 確認日 */
    checkedAt: string;
    /** その写真がこのスポットのものだと確かめたか */
    verifiedPlace: boolean;
};
```

- **`coverPhotoId`（#132・ユーザー投稿の写真ID）は残すが、公式ガイドの
  代表写真としては使わない。** 使うのは `coverImage` だけ。
  ユーザー写真を代表に採るなら、本人の公開設定・削除の扱いを確認したうえで
  `coverImage` に**明示的に写し取る**（削除されたら画面から消えるよう
  `photoId` も併記し、描画時に公開状態を見る）
- **無ければ無関係な写真で埋めない。** 撮影地名＋地図を中心とした代替レイアウト
  （§7・§8）

### 公開の線（`status` と「正式公開」）

```
draft      … ページを作らない（URL も無い）
published  … ページを作る
```

**`published` かつ「最低情報」を満たすものだけ `index`**（§10）。

## 4. 最初に登録するスポットの候補と選定理由

### ⚠️ 先に正直に書く

**この環境から外部サイトに出られない。** 実測:

```
https://www.mlit.go.jp/            000
https://www.city.kanonji.kagawa.jp/ 000
https://ja.wikipedia.org/…          000
https://nominatim.openstreetmap.org 000
```

環境のネットワーク方針がホストを拒否している。**つまり私は自治体・観光協会・
公式サイトの情報を自分で確認できない。** 確認日と出典を伴う事実は
**owner が入れるか、環境の Network access を広げてもらう**必要がある
（セッションのタイトルバーの環境メニュー → Edit → Network access）。

なので以下は「**候補の骨組みと、何を確認すれば埋まるか**」で、
**事実そのものは1つも書いていない**。

### 実データから確実に言える候補（4件）

owner 自身が撮っていて、**地点として特定できる**もの。

| # | スポット名（暫定） | 地域 | いま在る情報 | 代表写真の候補 | 画像の利用権限 | 不足している情報 | 公開可能か |
|---|---|---|---|---|---|---|---|
| 1 | 高屋神社 | 香川県 観音寺市 | 撮影地の文字列・写真1枚 | **owner の写真**（`location` が一致） | owner 本人＝明確 | 座標・概要・見どころ・季節・時間帯・構図・アクセス・駐車場・注意点・公式サイト | ❌ 追加確認が要る |
| 2 | 国営ひたち海浜公園 | 茨城県 ひたちなか市 | 同上・写真1枚 | **owner の写真** | owner 本人 | 同上 | ❌ |
| 3 | オペラ・ガルニエ | フランス パリ | 同上・写真1枚 | **owner の写真** | owner 本人 | 同上 | ❌ |
| 4 | 山中湖 | 山梨県 南都留郡 | 同上・写真2枚 | **owner の写真** | owner 本人 | 同上。**「山中湖」は湖全体＝地点か地域かの線引きが要る** | ❌ |

### ⚠️ 「写真がある」を「そこで撮った」と同一視しない

指示のとおり。**いま分かるのは `location` の文字列だけ**で、
被写体と撮影位置が同じとは限らない（高屋神社は麓からも撮れる）。
代表写真に使うときは owner の確認が要る。

### 残り16〜26件の作り方（提案）

実データにある**地域名**（フランス・パリ・東京・北海道・大阪・福岡・
バルセロナ・フィンランド・ヴェルサイユ）は**スポットではない**ので、
そのまま登録しない。代わりに:

1. **owner が実際に行った地点を挙げてもらう**（写真の有無は問わない）
2. その中から「場所を特定できる／公式情報が確認できる／地図に出せる／
   撮影ガイドとして紹介できる／代表写真を用意できる」を満たすものを選ぶ
3. **写真が用意できるもの**と**情報だけのもの**を `status` で分ける

**私からスポット名を提案しない。** 行ったことのある場所は owner にしか分からず、
「有名だから」で並べると §6 の選定基準（実際に確認できる）から外れる。

## 5. 代表写真を安全に用意する方法

| やること | どうやるか |
|---|---|
| **owner の写真を使う** | いちばん安全。`license: "owner"`。既に S3 に在るものを `coverImage.src` に指定（**ユーザー投稿の一覧とは別扱い**） |
| **許諾を取った写真** | `license: "permission-granted"` ＋ `sourceUrl`（許諾のやり取りの記録）＋ `requiredCreditText` |
| **CC ライセンス** | `license: "cc-by"` など。**商用利用・加工・再配布の可否を確認**してから。クレジットは必ず画面に出す |
| **やらないこと** | 観光協会・自治体・Google マップ・SNS の写真を無断で複製しない。**出典 URL があることと転載できることは別**。AI 生成の風景を「撮影スポットの記録」として出さない |
| **無い場合** | 代替レイアウト（地図＋スポット名）。**無関係な写真で埋めない** |

**機械で縛る**: `coverImage` があるのに `credit` か `checkedAt` が空なら
**ビルドを落とす**（テストで固定）。人の注意力に頼らない。

## 6. 情報の収集・更新・確認方法

### 置き場所の比較（依頼の A / B / C）

| | A: リポジトリ内（`content/spots.json`） | B: DynamoDB | C: 運営専用の管理API |
|---|---|---|---|
| 更新方法 | ファイルを直して PR | 管理画面 or CLI | 管理画面 |
| 反映 | **再ビルドが要る**（静的書き出しなので B・C でも同じ） | 再ビルドが要る | 再ビルドが要る |
| 誤編集の防止 | **PR のレビュー・型・テスト**（いちばん強い） | 無い（直接書ける） | 実装しだい |
| 費用 | **0** | テーブルは既存だが、同期スクリプト・IAM・`provision-env`・診断・staging の面倒が増える | 上に加えて Lambda と口の実装・保守 |
| 将来の拡張 | 件数が増えると1ファイルが重い（数百件までは平気） | 件数に強い | いちばん柔軟 |
| 出典・確認日 | **git の履歴がそのまま監査ログ**（誰がいつ何を書いたか） | 自前で持つ | 自前で持つ |

**推奨は A。** 理由は3つ:

1. **静的書き出しなので、どこに置いても「すぐ反映」にはならない**
   （develop の `spotMaster.ts` が既に同じ判断を書いている）
2. 公式ガイドは**人が書く文章**で、レビューを通す形がいちばん合う。
   git の履歴が「いつ確認したか」の裏付けになる
3. **費用0・新しい AWS リソース0**（§10）

**B へ移す線**: スポットが200件を超える、または owner 以外が編集するようになったら。
そのときも `Spot` の型はそのまま使えるよう、**読み込みは `lib/data/spots.ts` の
1関数に閉じる**（画面は置き場所を知らない）。

### 収集の手順（owner と分担）

1. owner が対象スポットを決める
2. **公式サイト・自治体・観光協会で事実を確認**（← 私は外部に出られないので owner か、
   ネットワークを広げてもらう）
3. `content/spots.json` に **確認できた項目だけ**書く。項目ごとに `sources`
4. PR を出す → 型とテストが「出典の無い項目」「クレジットの無い画像」を落とす
5. 変わりやすい情報は `checkedAt` を見て**定期的に見直す**

**文章は Journey Photo 独自のもの**（公式サイトの説明文を大量転載しない）。
**事実**（所在地・アクセス・注意点）と**運営の撮影アドバイス**
（構図・時間帯）は、型の上でも画面の上でも分ける。

```
│                              │  周辺スポット        │
└───────────────────────────┴──────────────────┘
```

**右カラムの `sticky` は、ホームの柱と同じ形にする**——
`lg:sticky lg:top-[88px] lg:max-h-[calc(100vh-168px)] lg:overflow-y-auto`。
理由はホーム側のコメントが書いている: **上だけで留めると、画面が低いときに
柱の下の節へ永久に届かない**（1280×600 で実測済み）。中で送れる箱にする。

## 11b. 🔴 台帳をクライアントに載せない（2026-09-23 に実測）

`content/spots.json` は**人が書く棚**で、1件ごとに概要・見どころ・季節・
時間帯・構図・注意点・アクセス・出典まで持つ。`lib/data/spots.ts` は
`import spotsJson from "@/content/spots.json"` で**丸ごと**読むので、
`"use client"` のファイルがそこから `SPOTS` を読むと**全文がそのページの
チャンクに載る**。

台帳に1件だけ入れて、本番と同じ設定でビルドして数えた:

    修正前  クライアントのチャンクに台帳の中身が載る
              49896f429396482b.js  → out/saved-spots.html
              59b11b77059e2248.js  → out/photo/*.html   ← **写真ページ30枚すべて**
    修正後  0本

写真ページは**検索の着地点**で、CLAUDE.md の優先度（表示速度）に直接当たる。
**JSON のモジュールは項目単位で落とせない**（台帳 `3ed31141` が `photos.json`
で同じ形を踏んで `photo-index.json` を作った）ので、減らす手は1つ——
**クライアントから台帳を import しない**。

  - 解くのは `lib/data/spotLink.ts`（`spotLinkForPhoto` / `spotLinksBySlug`）。
    **呼んでよいのはサーバー側だけ**
  - 画面が受け取るのは `SpotLink`（スラッグ・名前・地域・座標・代表写真の5つ）。
    **「出すかどうか」の判断もサーバー側で済ませる**（`usesMapHero` /
    `needsVisibleCredit` を画面に持ち込まない）
  - 見張りは `app/__tests__/spotLedgerClientImport.test.ts`——`"use client"` の
    ファイルが台帳を**値として** import していたら落ちる（型だけの import は通す）

**`SpotLink` に項目を足すときは「本当に画面が読むか」を確かめること**
——足したぶんが写真ページ30枚のチャンクに乗る。

## 11c. 🔴 台帳は「運営未確認の下書き」として出す（2026-09-25 の決着）

§11 の「事実は owner が入れる」は守られなかった。PR #163/#164 で Claude の
セッションが 1,417件を1日で書き、**外部サイトへ出られない環境のまま**
（PR 本文が「到達できない」と明記）全件に `verified: true`・
`verifiedAt: "2026-09-24"` を付けていた。画面はそれを「情報の最終確認:
2026-09-24」と全ページに描き、サイトマップ 1,522本の 96% が誰も確かめて
いない文章になるところだった。810件は本文に `**強調**` が生のまま残っていた
（＝ページを誰も読んでいなかった）。

**決めたこと**（owner の「方針は私の代わりに考えて」への答え）:

| | 下書き（`status: "review"`） | 公開（`status: "published"`） |
|---|---|---|
| 条件 | `reviewBlockers` が空（確認日は見ない） | `publishBlockers` が空 ＝ **`verifiedBy`（人名）と `verifiedAt` が対で揃う** |
| ページ | 建てる。帯「下書き（運営未確認）」・`noindex,follow` | 建てる。帯なし。「情報の最終確認: 日付（運営）」 |
| サイトマップ | **載せない**（`/spots`・県の一覧も `publishedCount` で見る） | 載せる |
| 「公式」の語 | 名乗らない（地図・一覧・読み上げも「下書き」） | 名乗る |
| 公式サイトのリンク | 「未確認のリンク」＋ `rel=nofollow` | そのまま |
| アクセス・駐車場・注意点（出典が要る項目） | **無条件に出さない**（住所と地図は出す） | `checkedBy` 付きの出典があるときだけ |
| アプリ向け JSON（`/app/data/spots.json`） | `stage: "review"` で載せる | `stage: "published"` |

- `verified`（真偽1つ）は**型ごと消した**。AI が true と書けば通る門だった。
  確認は `verifiedBy`（人名）でしか主張できず、`spotsLedger.test.ts` が
  AI の名前（claude / gpt / assistant …）を拒む
- 台帳の変換は `scripts/spots-review-stage.mjs`（冪等）。対象は旧い
  `verified` を持ち 2026-09-24 に作られた行（AI の行）だけで、人の行は触らない。
  ledger test が「掛けて差分0」と「旧い `verified` の鍵を持つ行は無い」を

  ——`npm run verify` は本番と同じ環境変数で建てるので、env で分けると

- 実測（2026-09-25）: 変換後 review 1,417・published 0・`**` 0。
