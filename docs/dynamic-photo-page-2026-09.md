## 1. なぜ「②が前提」が誤りだったか

### C（同行者の共同アルバム・招待リンク）

**招待ページに SEO は要りません。**むしろ検索に出てはいけない。
つまりサーバーで HTML を作る理由が無く、**静的な受け皿 + クエリ文字列**で足ります。

```
https://journey-photo.com/j?t=<トークン>
```

`/j` という静的ページを1枚置き、開いた JS が `location.search` からトークンを読んで
API を叩く。**この形はこのサイトで既に3か所 動いています**——`/?photo=<id>`（共有リンク）、
`/users?id=<uid>`、`/user/edit?id=<id>`。実績のある形で、追加のインフラは0です。

`/j/<トークン>` のようなパス形式にしたい場合だけ②が要ります（静的書き出しは
`dynamicParams = false` で列挙外を404にするため）。**見た目の好みのために
アーキテクチャを変えるのは順番が逆**です。

### E（貼って気持ちいい共有カード・動的OGP）

OG 画像は**書き込みのときに1枚作って S3 に置けば済みます**。
クローラが見るのは HTML の中の `og:image` の URL で、その画像が
「要求のたびに生成された」必要はありません。

- 写真ページ … **いま既に写真そのものを使える**（サムネと AVIF は生成済み・追加コスト0）
- 場所ページ … 「地名 + 枚数 + 代表写真」の合成カードは、投稿時に Lambda で1枚だけ作る

**やってはいけないのは「要求のたびに生成」**です。CDN のキャッシュヒット率が落ち、
Lambda の同時実行（アカウント全体で10）を真っ先に食い潰します。

## 2. いまの作りが本当に頭打ちになる線

### 1回の再ビルドの中身（Deploy Site run 360 の実測・合計7分02秒）

| ステップ | 時間 | 削れるか |
|---|---|---|
| **テストの実行** | **4分34秒（65%）** | **削れる**（下記） |
| コンテナの起動 | 46秒 | 削れない |
| S3 への反映 | 45秒 | 既に差分のみ（ETag=MD5 で比較） |
| **ビルド（140ページ生成）** | **21秒** | もともと安い |
| 依存のインストール | 14秒 | キャッシュ済み |
| サムネ生成 | 1秒 | — |

**サイトを丸ごと作り直すのは 21秒**です。「毎回フルビルドは重い」の中身は、
ほぼ**テストの再実行**でした。

### なぜテストを飛ばしてよいか

写真の投稿で起動される再ビルド（`repository_dispatch`）は、**コードが1行も
変わっていません**。その commit のテストは main への push のときに既に通っています
（`deploy.yml` の同じジョブで）。同じ木に対して2度目を走らせているだけです。

飛ばすと **7分 → 約2分**。

### 頭打ちの線（計算）

- 月の Actions 枠: **2,000分**
- 再ビルドの上限: `REBUILD_MONTHLY_MAX = 200`（既定値・リポジトリ変数で変えられる）

| | 1回 | 月200回 | 枠に対して |
|---|---|---|---|
| いま | 7分 | 1,400分 | **70%** |
| テストを飛ばす | 2分 | 400分 | **20%** |

テストを飛ばせば上限を **200 → 800** に上げられます（1,600分＝80%）。
畳み込み（10分）があるので、投稿1件がだいたい依頼1件です。

> **今の作り: 月200投稿（1日約7枚）で頭打ち**
> **テストを飛ばして上限を上げた場合: 月800投稿（1日約26枚）**

**この線を超えたら②へ。** 超える前に移るのは、まだ要らない複雑さを買うことになります。

なお**壊れ方は「遅くなる」ではなく「止まる」**です。上限に達すると
`requestSiteRebuild` はその月いっぱい false を返し、**写真の削除・退会の掃除まで
全部落ちます**。だから上限は「余裕」ではなく「安全装置」で、投稿が増えたら
必ず一緒に見直す必要があります。

## 3. ②の設計（線を超えたときに使う）

### 3-1. 何を動的にするか

**写真ページ（`/photo/<id>`）だけ。** 一覧・場所・カテゴリ・タグ・地図・
プロフィールは静的のまま S3 に置きます。理由:

- 写真ページは**新しく増える**。それ以外は「増えた写真が載る」だけで、
  多少の遅れが許される
- 静的のまま残せば、**動的な部分が落ちてもサイトは生きています**

### 3-2. 置き場の候補（AWS の中で）

| 案 | 形 | 良い点 | 悪い点 |
|---|---|---|---|
| **(c) 一度だけ作って S3 に書く** ★推奨 | CloudFront が 404 → Lambda が組み立てて **S3 に書き、返す**。2回目からは純粋な静的 | **表示ごとの費用が0**。S3 が引き続き真実。落ちても既存ページは無事。今の配信構成をほぼ変えない | 「作る人」を1つ書く必要がある |
| (b) Next をサーバーで動かす | `output: standalone` → Lambda + Function URL、静的資産は S3 | Next の機能（ISR・動的OGP・`next/image`）が全部戻る | 実質サイト全体の移設。コールドスタートが LCP に乗る |
| (a) Lambda@Edge | エッジで組み立て | 速い | DynamoDB が東京にあるのでエッジから遠い。デプロイが us-east-1 固定で運用が別物になる |

**(c) を推します。** このサイトは写真ページが**内容で固定**（uuid の URL・編集は稀）
なので、「一度作ればあとは静的」が素直に効きます。実質「フレームワーク無しの ISR」です。

### 3-3. (c) の具体

```
利用者 → CloudFront
           ├─ /photo/<id>.html がある     → S3 からそのまま（今と同じ）
           └─ 無い（403/404）            → オリジンフェイルオーバー
                                            → Lambda（写真ページを組み立てる）
                                               ├─ DynamoDB から1件読む
                                               ├─ HTML を組み立てる
                                               ├─ S3 に置く（次回から静的）
                                               └─ 返す
```

**編集・削除のとき**は、いまの `invalidateUploads` と同じ道具で
`/photo/<id>` を無効化し、S3 のファイルを消すか上書きします（削除経路の
CloudFront 無効化は**既に実装済みで staging で実証済み**）。

### 3-4. 立ちはだかるもの（実測で見つけたもの）

1. **カスタムエラー応答はディストリビューション全体に効きます。**
   `scripts/fix-cdn-error-pages.js` が 403/404 を `/404.html` に振り替えており、
   **ビヘイビアごとには分けられません**。(c) は「404 をきっかけに Lambda へ回す」設計なので、
   ここと正面衝突します。**オリジングループのフェイルオーバー**（S3 が 403/404 を
   返したら第2オリジンへ）を使えば、カスタムエラー応答を経由せずに回せます。
   ここは**実機で1回確かめてから**でないと設計を確定できません。

2. **HTML を2か所で作ることになる**（Next のビルドと、この Lambda）。
   このリポジトリが何度も踏んでいる「複製した規則は静かにずれる」型です。
   避けるには、**同じ React コンポーネントを Lambda 側でも `renderToString` する**
   （＝(b) に半歩寄る）か、**写真ページだけ Next のサーバーで描く**か。
   ここが (c) の一番の設計上の宿題で、**軽く見るべきではありません**。

3. **`REBUILD_DISPATCH_TOKEN` は②に移れば不要**になります。
   逆に言うと、①のまま行くなら要ります。

### 3-5. 費用の見積もり

写真ページの表示のうち、**S3 に無い（＝初回）ものだけ** Lambda が動きます。
月1,000枚の新規投稿なら、Lambda の起動は**月1,000回**程度（以後は静的）。
これは無料枠（月100万リクエスト）の 0.1% で、**実質ゼロ**です。

対して (b) は全ページビューが Lambda を通るので、月10万PVなら10万回。
それでも無料枠に収まりますが、**同時実行10の上限**（アカウント全体）に
先にぶつかります。
