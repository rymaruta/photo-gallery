# 撮影スポット機能 Phase 1 — 設計と実装（2026-09-21）

台帳（スポットマスタ）の土台を作るところまで。レビューと旅程は範囲外。

## 0. 先に実測したこと

判断の前提なので、推測ではなく数えた値を置く（すべて 2026-09-21 実測）。

| 見たもの | 値 | どこで数えたか |
|---|---|---|
| 公開写真 | 30枚 | `app/data/photos.json` |
| 撮影地の文字列を持つ写真 | 17枚 | 同上 |
| 撮影地の異なり | 14種 | 同上 |
| うち**個別の地点**と言えるもの | **4種**（高屋神社 / 国営ひたち海浜公園 / オペラ・ガルニエ（パリ）/ 山中湖） | 同上 |
| 残り10種 | 東京・大阪・福岡・北海道・パリ・フランス… ＝**地域** | 同上 |
| **座標を持つ写真** | **0枚** | 同上（`geoApprox` も0） |

**ここがこの設計でいちばん効く事実**:

- `/location/*` は**地域と地点が混ざった棚**。スポットページは
  「地点だけの棚」なので、`/location/*` を置き換えるものにはならない
- **座標での近傍検索は、いま答える材料が無い**。座標は写真にも0枚、
  あっても保存時に**約1kmへ丸めてある**（`sanitizeCoords`）。
  だから「座標だけで同じ地点と判断する」設計は最初から採らない

## 1. DynamoDB 設計 A / B の比較

- **A**: 既存の `prod-photo-gallery-photos` に `spot#<spotId>` の行を同居させる
- **B**: 専用テーブル `prod-photo-gallery-spots` を新設する

| 観点 | A（既存テーブルに同居） | B（専用テーブル） |
|---|---|---|
| パーティションキー | `id = "spot#<spotId>"`（既存のPK1本に乗る） | `spotId` |
| ソートキー | 無し（写真テーブルにソートキーが無い） | 無し／`sk` で版を持てる |
| GSI の要否 | **Phase 1 では不要**（下記 2） | 地域一覧・近傍で最低1本要る |
| ID 引き | `GetItem`（PK 一発） | `GetItem`（PK 一発） |
| 名前検索 | 静的 JSON 上で実施（数十〜数百件） | 同左。件数が万を超えたら GSI か検索基盤 |
| 地域一覧 | 静的 JSON 上で実施 | `region` の GSI |
| 近傍検索 | 静的 JSON 上で実施（**座標が1km丸めなので粒度はそこまで**） | geohash の GSI |
| 写真との紐づけ | 写真行に `spotId` 属性を足すだけ | 同左（テーブルは別でも紐づけ方は同じ） |
| 将来の人気集計 | ビルド時に写真から数える（カウンタを持たない） | 同左。書き込み集計を足すなら B が素直 |
| 読み負荷 | **増えない**——台帳はビルド時の Scan 1回に相乗り | 台帳ぶんの Scan/Query が1回増える |
| 書き負荷 | 台帳の更新のみ（極少） | 同左 |
| 運用費 | **+0 円**（行数十件・オンデマンド・既存 Scan に相乗り） | 保存量ぶん（数十件なら月 0.01 USD 未満）＋**運用の手間**（provision-env / IAM / 環境変数 / 診断の全部にテーブルが1つ増える） |
| 既存データへの影響 | **無し**。`spot#` 行は `src` を持たないので、`photos.json` を作る絞り込み（`item.src`）で落ちる。既存 GSI3本の鍵（`userId` / `storyFeed` / `publicFeed`）も持たないので索引にも載らない | 無し |
| 取り消しやすさ | 行を消すだけ | テーブルごと削除（本番リソースの増減が要る） |

### 採ったのは **A**。理由

1. **前例がそのままある。** このテーブルは既に単一テーブル設計で、
   `comments#` `notifs#` `followstats#` `geocache#` `syncstats#` `rebuild#lock`
   が同居している。`spot#` は6つ目の同居人で、新しい考え方を持ち込まない
2. **本番リソースを1つも増やさずに Phase 1 が完結する**
   （新設・GSI追加は owner の確認が要る領域。そこを踏まずに進める）
3. **読み取りを1回も増やさない。** 台帳はビルド時の Scan
   （`sync-photos-from-ddb.js`）に相乗りして `app/data/spots.json` になる。
   画面もアプリもこの静的 JSON を読むので、**実行時の DynamoDB アクセスは 0**
4. B へ移るのはいつでもできる。`spotId` が写真側の参照なので、
   台帳の置き場所が変わっても写真データは無傷

### B に移すべき合図（先に決めておく）

- 台帳が **数千件**を超える（静的 JSON を丸ごと配るのが重くなる）
- 利用者がスポットを投稿するようになり、**実行時の書き込み**が増える
- 「近くのスポット」を**1km より細かく**答える必要が出る
  （＝座標の丸めを変える判断が先に要る）

## 2. GSI は今のところ足さない

Phase 1 で要る問い合わせは次の4つで、**どれも GSI 無しで答えられる**:

| 問い | どう答えるか |
|---|---|
| ID で引く | `GetItem`（PK） |
| 名前で探す | `app/data/spots.json` 上で `searchSpotsByName` |
| 地域で並べる | 同上 `spotsInRegion` |
| 近くを探す | 同上 `nearbySpots`（1km丸めの座標に見合う粒度） |

**足すとしたら** `spotFeed`（台帳の行にだけ入れる定数）+ `updatedAt` の
疎な GSI。`storyFeed` / `publicFeed` と同じ手で、**owner の承認が要る**。
いま足さないのは、ビルド時の Scan が1回で済んでいる間は要らないから。

## 3. 費用の見積もり

- **A（採用）**: **月 +0 円**。行は数十件（1件 1KB 未満）、書き込みは台帳を
  直すときだけ、読み取りは既存 Scan に相乗り。オンデマンド課金の最小単位に
  すら届かない
- **B**: テーブル自体はオンデマンドなら基本料が無く、保存量だけ
  （**月 0.01 USD 未満**）。ただし GSI を1本足すと**保存量が倍**になり、
  provision-env・IAM・環境変数・診断まわりの保守が増える

## 4. 写真とスポットの結び付け方

規則は `lib/utils/spots.ts` の `suggestSpotLinks` に**1本だけ**置いた
（画面・アプリ・下見の道具が同じ規則で動く）。

1. **名前が一致しない写真は候補にしない。** 座標だけで同じ地点と決めない
   ——写真は座標を1枚も持っておらず、あっても1km丸め、さらに
   **被写体と撮影位置は別**（富士山は20km先からでも撮れる）
2. 同じ名前のスポットが**2つ以上**なら `ambiguous`。同名異所（清水寺・大手町…）を
   機械に選ばせない
3. 名前が一致しても**200km 以上**離れていれば `ambiguous`。
   被写体と撮影位置の差では説明できない距離＝同名異所の疑い。
   逆に「近いから」を根拠に**格上げはしない**（1 の理由）

`confirmed` だけが書き込んでよい候補。**保留と対象外は未設定のまま残す。**

下見の道具（既定はドライラン）:

```bash
tsx scripts/link-photos-to-spots.ts                      # 本番を読んで下見（書かない）
tsx scripts/link-photos-to-spots.ts --from-json mock.json # 手元のデータで下見
tsx scripts/link-photos-to-spots.ts --apply              # 確定ぶんだけ書き込む
```

`--apply` でも:

- 足すのは `spotId` だけ。**`location` は消さない**（`/location/*` は今までどおり）
- `attribute_not_exists(spotId)` 付き＝**人が直したものを巻き戻さない**
- 公開・非公開は触らない

## 5. `/location/*` との関係

**一律リダイレクトはしない。** 役割が違う。

| URL | 何の棚か | 元になるデータ |
|---|---|---|
| `/location/<文字列>` | 撮影者が打った**撮影地の文字列**の集約。地域（東京・フランス）も含む | 写真の `location` |
| `/spots/<slug>`（Phase 1.5） | **台帳のある個別地点**。住所・地域・種別・地図を持つ | `spot#` 行 |

- 既存の `/location/*` は**そのまま生かす**。生成条件も枚数の線
  （`MIN_INDEXABLE_LOCATION = 2`）も変えていない
- `slug` は**作ったときに決めて、改名しても変えない**。だから
  正式名を直しても URL が動かない＝リダイレクトの層が要らない
  （静的書き出しにはリダイレクトの層が無いので、これは設計上の要点）
- **canonical**: スポットページは自分自身。`/location/<X>` の中身が
  スポットページと事実上同じになった場合だけ、その**撮影地ページの
  canonical をスポットページへ向ける**（リダイレクトではない＝既存の
  リンクも検索結果も 404 にならない）
- **サイトマップ**: スポットページは**紐づいた公開写真が2枚以上**のときだけ
  載せる（撮影地ページと同じ線。1枚のページは写真の個別ページと中身が同じ）
- **内部リンク**: 写真ページ → スポットページ（`spotId` があるとき）、
  スポットページ → 撮影地ページ・近くのスポット、の双方向

**Phase 1 では `/spots/*` のページ自体はまだ作っていない**（下の「やらなかったこと」）。

## 6. スポット台帳の項目

`lib/data/spots.ts` / `Sources/JourneyPhoto/Models/Spot.swift`（同じ形）。

| 項目 | 必須 | 意味 |
|---|---|---|
| `spotId` | ✔ | 鍵。**名前から作らない**（`sp_` + 16進）。改名しても変わらない |
| `slug` | ✔ | URL の綴り。作成時に決めて**変えない** |
| `name` | ✔ | 正式名 |
| `aliases` | | 別名・旧称・英語表記 |
| `address` | | 住所1行 |
| `region` | | `country` / `prefecture` / `city` |
| `coords` | | 公開座標（**写真と同じ約1km精度**） |
| `category` | | 神社 / 公園 / 山 … |
| `coverPhotoId` | | 代表写真（公開写真の id） |
| `status` | | `draft` は公開 JSON に出さない |
| `verified` | | 人が確かめたか |
| `createdAt` / `updatedAt` | ✔ | |

**同名異所を混ぜない**ための決まり:

- 一意なのは `spotId` だけ。**名前は一意キーにしない**
- 名前が同じ2件は**そのまま2件として持つ**（結び付けは `ambiguous` になり、
  人が選ぶまで写真は未設定のまま）

## 7. やらなかったこと（意図的に）

- **`/spots/<slug>` のページを作っていない。** 台帳が0件なので、作っても
  生成されるページは0枚。サイトマップ・テストだけが増える。
  台帳に最初の数件が入る回（＝ owner が地点を決める回）に一緒に出す
- **本番の DynamoDB に何も書いていない。** 台帳の行の作成も、写真への
  `spotId` の付与も、実行は owner の確認待ち
- **GSI を足していない**（2 のとおり、今は要らない）
- **件数・保存数・人気順位を出していない。** 画面に出る唯一の数は
  「この場所の写真（N）」で、これは**いま並んでいる枚数そのもの**
