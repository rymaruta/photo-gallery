### ⑩ を別画面（`/notifications`）にしなかった理由

- 一覧は **`NOTIFS_MAX = 50` で頭打ち**（`api-user/src/notify.ts`）。
  ページ送りが要らないので、全画面にする実用上の理由が無い
- 画面を足すと**通知を読む導線が2つ**になる
- ベルが積み上げてきた正しさ（取得世代・既読世代・`status` の3状態・
  ブロック除去後の未読数）を、写した側で作り直すことになる

モックが全画面なのは iOS のタブバーに枠があるから。Web はベルがその枠。

**通知の種別は4つ**（`like` / `comment` / `follow` / **`storyreply`**）で
タブは3つなので、**`storyreply` は「コメント」に畳んだ**。素直に
`type === tab` で絞ると、ストーリーへの返信が「すべて」以外のどこにも出ない。

🔴 **「新着」は位置ではなく時刻の境界で決める。** 未読は「先頭 N 件」＝
位置の意味を持つ数（`64a45d74`）。ここで踏み直した穴が2つあり、どちらも
レビューで出た:

- 境界を `usableRows` の**あと**の配列から数えていた。`unread` はサーバーが
  返した並びでの先頭 N 件なのに、`usableRows` は読めない行を1件ずつ抜くので
  **境界が既読側まで下がる**。生の `data.items` の位置から数える
- 「開いている間は下げない」だけにしたら、下げられるのが**閉じている間の
  ポーリング**（60秒に1回・裏タブでは走らない）だけになり、開いてすぐ
  閉じて開き直すと「新着」が居座った。`closePanel` で境界を捨てる

**区分は暦日で数える**（`calendarDaysAgo`）。転がる24時間のままだと、
午前1時に「今日 23:00」＝まだ来ていない時刻に見える。

### 🔴 `vi.mock` は黙る（この周でいちばん効く教訓）

**vitest は、存在しないパスを `vi.mock` しても何も言わない。** 実演:

    死んだ mock を1つ仕込む（移設前のパスに書き換える）
      → そのテストファイル自身   **13件 全緑**
      → 新しい見張り             **名指しで落ちる**

`/user/settings` への移設で死んだ mock が10ファイルに残っていたのは
これが理由。**効いていない mock を「効いている」と思い込む**（本物が
読み込まれ、ネットワークや重い依存がテストに入る）のが害。

見るのは**相対パスだけ**。`@/…` は `tsconfig` の `paths` を写す必要が
あり、写しがずれたときにまた黙るので対象外にした。

### 3. 横断して見える大きなもの

#### owner の判断が要るもの

1. **写真の公開範囲は `published` の真偽しか無い**（P7）。「フォロワーのみ」は静的書き出し（`/photo/<id>` の HTML・サイトマップ・`publicFeed` 索引・`GET /photos`）に乗らない経路を新設する話。SEO 面積（検索に載るページ数）に直接響くので、方向性（検索流入優先）と突き合わせて決める必要がある。
2. **スポットの実体（マスタ）が無い**。撮影地は写真の `location` 自由文字列を束ねているだけ。これに掛かるのが E3 注目スポット・E4・L2・L3 公式名/ふりがな/評価/口コミ・L5 紹介文・L7 行きたい人数・L9・Y10 国・C3。現コードは「クチコミは作らない」（`SpotPageClient.tsx:40-45`）「紹介文は生成しない」（`lib/utils/spot.ts:12-21`）と owner 指示を記録済み。iOS ブランチ（d4ac298b・`spot#<id>`）に台帳の土台があるが develop 未マージ。**評価・口コミを足すかどうかが分岐点。**
3. **データに無いプロフィール項目**: 認証バッジ（D2・Y1。誰が認証するかの決めが要る）・居住地（Y1・Y9）・国（H2 の輪・Y10）・訪れた国（Y3）。総移動距離は実装済みだが coords 0 で本番は出ない。

## 設計で決めていること

### 複数枚は `src` を配列にしない

`src` は**1枚目（表紙）のまま**にして `extraImages` を足す。理由:

- 既存30枚は `extraImages` を持たないので**何も変わらない**（後方互換）
- 表紙が `src` のままなら **og:image・サムネ・地図・サイトマップ・JSON-LD の
  入口を1つも書き換えずに済む**
- 派生（`thumbSrc`/`srcAvif`/`width`/`blurDataURL`…）は1枚ごとに要るので、
  `extraImages` の要素も同じ形を持つ

### 「同じものを二度作らない」で効く既存の部品

| やること | 既にある形 |
|---|---|
| 保存の一覧 | `likes#<uid>`（`api-user/src/userList.ts` の `updateUserList`。共有済み） |
| アーカイブで実体を残す | `keptAs`（`cleanupExpiredStories` が印を見て S3 を残す） |
| 投稿の2択 | `PostSheet`（「入口が増えたら呼ぶだけ」とファイルに書いてある） |
| 画面下のバーの高さ | `useBottomBarHeight`（`--bottom-bar-h` に実測値を出す。`MiniPlayer` が読む） |

### ハイライトは「本体 ＋ 利用者ごとの一覧」で、ストーリーの行は写さない（⑦・2026-09-21）

`highlight#<hid>`（`ownerId`・題・`storyIds`・表紙）と `highlights#<uid>`
（`updateUserList` の行）。アルバムと同じ形で、**ストーリーの行は ID で
指すだけ**——写すと本人がアーカイブから消したあとも写しが残り、
「消える」約束が破れる。読むときに無ければ落とす。

- **ハイライトは誰でも見られる**（マイページの輪）。だから入れられるのは
  「アーカイブに自動保存」かつ「全員に公開」で投稿した分だけ。
  フォロワーのみの投稿は**黙って公開に変えず、断る**（画面は鍵を付けて
  押せなくし、サーバーも 400 で返す）。owner が緩めたければ、ここを
  「入れた時点で公開になる」に変えるのは1か所（`checkStories`）
- 読む2つの口は未認証（`PublicReadRole`＝写真テーブルは GetItem のみ）。
  Query が無いので ID を1件ずつ引く＝**1人20個・1つ100件**の上限がある
  （`lib/highlights.ts` と対。`highlightParity.test.ts`）
- 訪問者に返す形は**要る列だけを明示**（閲覧者・返信の数・`keptAs`・
  S3 のキー・座標は出さない）。`allowReplies: false`・`archivedAt` を必ず
  埋めるので、ビューアは返信の帯・閲覧者・「残す」・閲覧の記録を出さない
- 画面: `HighlightsRow`（輪。`StoriesBar` と同じ 64px・色は `ring.ts` に
  寄せた）／`/user/highlights`（作る・直す・消す。タイルはアーカイブと
  同じ `StoryTile`）。保存は投稿順（古い→新しい）

### 撮影スポット詳細は `/location/<スラッグ>` を育てた（2026-09-21）

**`/spot/...` は作らなかった。** 作ると「場所のページ」が2つになる——
このリポジトリが何度も踏んでいる型（同じものを二度作る）。

- 本体だけ `SpotPage` に差し替え。**`generateStaticParams` と
  `generateMetadata`（canonical・サイトマップ・`noindex` の判定）は
  `lib/server/collections.ts` のまま無改変**。タグ・カテゴリ・機材は
  `CollectionPage` のまま
- **実ビルドで前後を数えた**（`out/` の出力）:

      /location のページ   14
      noindex               9
      サイトマップに載る     5     ← 作業前に本体の関数で数えた値と同じ
      サイトマップ全体      53

- タブ（概要／写真／地図）は**3つとも DOM に残して `hidden` で隠す**。
  検索に載っているページなので、本文が HTML から消えてはいけない
  （実ビルドの `out/location/パリ.html` で3パネルとも在ることを確認）。
  **既定は「写真」**——今まで見えていたものを保つ
- **クチコミは作らない。** 投稿する口も裁く仕組みも無いのに枠を置かない
- **概要に紹介文を生成しない。** `spotFacts`（`lib/utils/spot.ts`）が

- 地図は `/map` へのリンクだけ（`app/map/` は別の作業中）。
  **`/map` は中心を指定するクエリを受け取らない**ので、いまは

  受け口を持った日に、ここのリンクへ足せばよい

### スポットの同一性は、新しい統合を入れなかった（実データで数えた）

    撮影地 14種 / 索引に載る 5 / 載らない 9
    包含（向きあり・`photoIsInLocation`）4組:
        フランス ヴェルサイユ    → フランス
        オペラ・ガルニエ（パリ）  → パリ
        パリ, フランス           → フランス
        パリ, フランス           → パリ
    `sameLocation`（対称）でしか拾えない追加の組: **0**

実質的な重複は `パリ`(3枚) と `パリ, フランス`(1枚) の1組だけで、
**後者は1枚なので既に noindex**＝検索面積の害は出ていない。ここを
機械的に寄せると「別の場所を誤って統合する」側に倒れるので、
**統合せず、包含関係を画面に出す**（「より広い撮影地」「この場所の中の
撮影地」）に留めた。

**地名の上下関係を当てに行く仕組みは持っていない。** `photoIsInLocation` は
文字列の包含なので、`"パリ"` は `"フランス"` を含まない——`/location/パリ` に
「フランス」は所在地として出ない。**これは仕様**で、当てに行くと
「パリ」が実はテキサス州のパリだった、のような誤った統合が入る。

### 行きたい場所は `updateUserList` を使い回した

- `spots#<uid>`（新しい順のリスト1行 ＋ `rev` の CAS）。`following#` `likes#`

- **いいねと違ってマーカーを置かない。** あちらは「済みか」をマーカーが
  決めるので一覧が欠けても直せるが、こちらは**一覧が唯一の状態**。
  だから `noteLiked` のように飲み込まず、書けなければ 500（競合は 503）
- **本人だけが見られる。** 行 ID は JWT の `sub` からしか作らない
  （他人の一覧を指すパスが存在しない）。入力を変えても読む行が変わらない
  ことをテストで固定
- **退会で消す。** `account.ts` の既知キーの削除に足した。決定的キーの
  自分の行で、本人しか読めない一覧なのでここで消せば完全に消える

    `spots#` / `saves#` の隣に1行足した。消さなかった間、退会後も
    「何にいいねしたか」が最大1000件（`LIKED_MAX`）残り、掃除役が居なかった。
    - **`like#<photoId>#<uid>` のマーカーは残る**（`saves#` と同じ理由——
      ソートキーが無く前方一致で列挙できない）。ファイル冒頭の

    - **写真側の `likes` カウンタは減らさない。** フォローの掃除は相手の
      `followers` を減らすが、あちらは `following#<uid>` が完全な台帳で
      「マーカー削除＋減算」を1つの取引にできるから。いいねの一覧は
      `LIKED_MAX` で溢れ、`noteLiked` が書き込みの失敗を握るので
      **一部だけ減る**ズレを作る。取引にしても最大1000件は

    **`save#<photoId>#<uid>` のマーカーは残る**——ソートキーが無く前方一致で

### 注意

- **寸法と字は px で書く。** 640px 未満で root が 14px になるので、
  `w-11` は 38.5px・`text-lg` は 15.75px に縮む（`96eb86db` で踏んだ）
- **ボトムタブバーは常駐する。** `PostSheet` は「常駐する場所に置く日が来たら、

## 4つの独自機能（2026-09-21・本番の実データで数えてから決めた）

owner の指示は Photo Quest → Color Journey → Moment Match → Photo Relay。
**作る前に本番の公開API（`GET /photos`）で数えた。** コミット済みの
`app/data/photos.json` は古いうえ派生の欄が落ちた断面で、数える土台に
ならない（30枚・`dominantColor` 0・撮影日 8）。本番は **39枚・投稿者2人

### Color Journey で決めたこと

- **新しい画像解析は作らない。** 既にある `dominantColor` で数えて足りた
- **チップは決め打ちで10個並べない。** 中身のある色だけ・最小2枚（撮影地の
  線と同じ）。手元の断面は色を1枚も持たないので**部品ごと何も描かない**——
  それが正しい姿で、テストが固定している
- **彩度を先に見る**（`s<.10` でだけ無彩色へ）。明度で先に切ると夜・北欧の
  写真が黒に落ちて **46%** が1つのチップに入る（彩度優先なら 36%）。
  ただし**明度 0.08 未満は色味があっても黒**——HSL の彩度は真っ黒に近いほど
  跳ね上がり、`#180808`（明度 0.063）が「赤」になっていた（レビューで発見・
  本番3枚が該当）
- ~~**`GalleryPageClient` を触らないことで残る3つ**~~ → **解いた（#72 のあと）。**
  部品を `app/components/ColorJourney.tsx` に移し、`GalleryPageClient` の
  「さがす」面が **`filteredPhotos`・`openById`・`categoryDisplayMap` を渡して描く**
  形にした。写真を取りに行く部品ではなくなったので:
  `usePhotos` は1つ／色のグリッドも下と同じモーダルで開く／色の内訳は
  **絞り込み後の一覧の中**で数える（タグの件数バッジと同じ考え方）。
  `app/__tests__/GalleryPageClient.colorJourney.test.tsx` が3つとも固定
  （修正前のコードで 4/5 落ちることを確かめた）
- **限界: 緑・赤・桃・紫は本番で0枚。** `dominantColor` は最頻1ビン＝影の色に
  なりやすい。`blurDataURL` の分布なら緑が7枚立つところまで確かめたが、
  閾値で答えが変わり検証の術が無いので採らなかった。owner が数枚見て
  決められるようになったら差し替える
- 最初は `GalleryPageClient` に触らず `/search` の上に部品を足しただけだった
  （別作業中・トップと共用）。④-b が落ち着いたあとで中へ寄せた（上の項）
- 実ブラウザで確認済み（本番の色を手元で注入して build → Chromium で
  390px/1280px とも 5チップ・32px・選択で11枚・解除で0枚・横はみ出しなし）
